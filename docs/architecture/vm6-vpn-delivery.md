# vm6 VPN 链路与统一验收

Issue：#48。决定日期：2026-10-24。此文件是架构师、产品经理、iOS/Mac/Relay 开发与验收 agent 的当前网络依据，优先于历史文档中的旧公网地址和部署暂缓记录。它更新验收环境，不宣称实现或真机验收已完成。

## 用户已确认的链路

```text
iPhone 原生 App（Wi-Fi 关闭，蜂窝网络 + 用户 VPN）
    │ HTTPS，严格验证 CA、IP 和有效期
    ▼
vm6 Relay：100.100.81.209:9899
    ▲ WSS，由公司 Mac 主动连接
    │
公司 Mac Connector → HTTP 回环 Bridge（127.0.0.1:8787）
                       ├─ 本机 Codex → 授权项目/任务独立工作区
                       └─ 灵矽 AI WSS → 语音/草稿/状态查询/播报
```

| 项目 | 当前约定 |
| --- | --- |
| Relay 主机 | 个人 vm6，`100.100.81.209` |
| 手机 API 根地址 | `https://100.100.81.209:9899` |
| Mac 出站 Connector | `wss://100.100.81.209:9899/connector` |
| Relay 监听 | `0.0.0.0:9899`，启用 TLS；不因此授权开放其他端口 |
| 手机网络 | 蜂窝 + 用户已有 VPN；VPN 提供到 vm6 的路由 |
| Mac 网络 | 实际可达 vm6 的网络/VPN路由；仅出站，不开放公司 Mac 入站端口 |
| 信任 | 自建 CA；服务器叶证书 IP SAN 包含 `100.100.81.209`；Mac 信任公开 PEM，iPhone 签名资源包含经审核的公开 DER |
| 已退役入口 | `121.52.250.201` 属于另一台 bili-xs8，不是 vm6，不要求将其映射到 vm6 |

`100.100.81.209` 是共享地址段，不当作普通公网地址宣传。本次户外目标通过用户接受的 VPN 达成；不新增无 VPN 直连的承诺。VPN 不替代 HTTPS/WSS、配对、项目授权或版本/requestId 规则。

## 当前证据和实现缺口

以下来自用户在聊天提供的输出，文档协调者未独立登录服务器重跑：

- Relay 安装成功，用户启动 HTTPS 并确认监听从 `127.0.0.1:9899` 改为 `0.0.0.0:9899`。
- 用户 Mac 的 TCP 探测到 vm6:9899 成功；浏览器取得503 / `Mac is offline`。
- 服务器 curl 用 `--resolve 121.52.250.201:9899:127.0.0.1` 和 CA 返回相同503。这证明当时旧 IP 证书的本机 TLS，未证明新 IP 身份或手机链路。
- 用户确认手机开启 VPN 可访问 vm6。尚无同一签名 VoxCode 构建在蜂窝+VPN上的实际配对/任务证据。

已知待办：现有服务器叶证书签给旧 IP，需由部署负责人沿用受信 CA 为新 IP 签发叶证书，并验证后切换。若 CA 本身需轮换，必须同步审核/更新 Mac 与 App 的公开信任材料，不可静默换根。不要用 `curl -k`、浏览器忽略证书或关闭校验作为验收。

iOS 在此文档基线仍有旧地址：`BridgeTransport.fixedIP`、`Info.plist`、`SettingsView` 默认入口及对应测试。iOS 主责应按独立 Issue/PR 适配严格信任策略与测试；只编辑配对 URL 或 README 不够。当前文档 PR不修改这些实现，不代表已有可连新地址的 App。#44 的构建交付和 #35 的原生监控检查仍有各自门槛。

## 分层检查顺序

1. **服务器本机与监听。** 用 `ss -ltnp 'sport = :9899'` 核对监听及进程。现有回环503只能关闭本机网络这一层，不能关闭后续层。
2. **新IP的严格TLS。** 叶证书必须包含 `IP:100.100.81.209`。Mac通过SSH/SCP等可信通道取得公开CA，核对SHA-256指纹后执行下面命令。HTTP503 / `Mac is offline` 表示TLS/Relay已通、Connector未通；没有HTTP响应则继续排查网络/信任，不能改成HTTP。
3. **Mac执行链。** 启动授权项目的正常Bridge和唯一Connector，核对新WSS地址和公开CA；机器ID/密钥与Relay一致，不能放手机。健康响应反映Mac可达后，还要实际创建Codex任务、续接同一会话、检查真实diff/检查退出码。`codexAvailable`只代表可执行文件存在。
4. **手机安装与网络。** 同一签名iPhone构建，模拟模式关闭，确认新入口/CA资源，关闭Wi-Fi、启用蜂窝和VPN。通过App短期配对码配对指定Mac/项目；Safari收到JSON不替代此检查。
5. **真实业务闭环。** 灵矽语音→可编辑草稿→用户确认→真实Codex修改→进度/diff/检查→同任务追问→当前版本验收。按既有范围检查至少20个任务管理、默认四路/第五排队、录音目标固定、授权和停止。
6. **VPN/网络恢复。** 保持蜂窝但断开VPN，验证不崩溃、不降级HTTP、不把旧快照标成新状态；请求已发但响应丢失时保留原requestId/内容对账。恢复VPN后取回真实状态，不重复执行。开启VPN仍无路由时按实际不可达处理；同时验证Mac出站连接丢失/恢复，不能假定仅手机VPN恢复就恢复Mac。

Mac网络/TLS检查（替换为实际已核对的公开CA路径）：

```sh
nc -vz -G 5 100.100.81.209 9899
curl --noproxy '*' --connect-timeout 5 --max-time 20 \
  --cacert /path/to/verified/VoxCodeCA.pem \
  -i https://100.100.81.209:9899/api/health
```

此处不加 `--resolve` 回环映射、不忽略证书。负向工程测试应证明未知CA、错误IP、过期证书、明文远程连接被拒绝，既有配对/撤销/授权/重放规则继续有效。不要为VPN引入任意信任或全局ATS放行。

## 验收记录与关闭标准

每次记录：Issue/PR、commit、签名构建标识、iPhone/iOS版本、Wi-Fi关闭/蜂窝开启/VPN开启、时间、入口和CA公开指纹、Mac Connector/Bridge/Codex版本、任务/requestId、预期/实际、脱敏结果、失败/未验证项。不得记录VPN账号密码、私钥、会话令牌、机器密钥或原始私人音频。

证据分层：用户报告的部署/TCP输出、严格TLS、Connector、真实Codex/Linx、device安装、outdoor蜂窝+VPN分别记录，不能互相替代。App、Relay和Mac使用同一可核对配置/兼容版本，G4安装与G5户外关联同一签名构建。最终交付仍要求真实灵矽与Codex、多任务隔离和结果验收，不因VPN可访问或文档合并而完成。
