# 开发实践：主干、验收与契约

本规范落实用户选定的三项实践，适用于架构师、协调者和开发 agent。任务与 PR 按 [Issue 协作](../issue-collaboration.md)记录，权限和 review 门槛沿用 [CONTRIBUTING.md](../../CONTRIBUTING.md)；不新增平台、部署单元或 Actions 校验。用户最新明确要求优先。

## 1. 主干开发：小步集成到 master

- `master` 是最终集成主干。所有改动从 Issue 对应的 `codex/<issue-number>-<purpose>` 分支通过 PR 提交，禁止直接 commit/push 主干。存量分支保留原名，按现有迁移规范处理。
- 一个 PR 对应一个可单独审查、验证的行为或文档里程碑。计划中的工作尽量当天形成可审查切片；超过一天未集成时，架构师检查依赖和拆分机会，不能靠省略测试或 review 赶进度。
- 每个开发者使用独立 worktree 和独占路径；共享契约由协调者串行修改。协调者负责 stage/commit/push/合入，开发者按已有协议交接。
- 从最新 `origin/master` 创建分支，所有新 PR 均以 `master` 为目标。依赖 PR 尚未合入时，在 Issue/PR 中列出依赖并保持 Draft，不以其他 topic branch 为集成目标；依赖合入后更新到实际主干基线，重跑受影响的检查。
- 相关本地检查通过即可发布里程碑 Draft PR，让进展可见；转为可合并状态仍需完成规定 review。若主干更新影响接口、验证结论或合并结果，补做针对性验证；不复用失效的旧结论。
- 合入后按 [清理规范](cleanup-policy.md)核验依赖、merge SHA 和工作区状态，再由协调者清理已合并 topic。PR、review 和证据保留；dirty、未合并或仍被依赖的工作继续保留。

架构师每个检查点查看：有哪些待合 PR、各自依赖谁、哪个最小切片能先验证。避免长期维护相互偏离的端侧集成分支。

## 2. 验收驱动：先约定可观察结果

开始实现前，在 Issue 写清用户场景、前置条件、操作、可观察结果和证据等级。可用 Given / When / Then 三行表达，不强制引入 BDD 框架。验收条目必须能被复核，不能只写“体验好”“功能完成”或“测试通过”。

| 时点 | 必须留下的记录 |
| --- | --- |
| Ready | 用户场景、范围、验收条目、所需资源、检查方式、负责人和依赖 |
| 实现 | 按风险补充正向/负向覆盖；鉴权、串任务、版本、重放、取消等改变先复现风险，再修复 |
| 交接 | 实际 revision、命令、结果、环境、证据类别、未运行项和下一步 |
| Review/合入 | 检查 Issue 条目与代码证据是否对应，完成既有独立 review；未满足项留在明确的后续 Issue |
| 产品验收 | 按 [current.md](current.md) 的实现边界逐项核验 server-live、phone-live 和部署关口，保留实际环境与版本证据 |

文档改动用内容/链接检查；运行时改动用相应组件、契约或集成检查，避免为文档制造行为测试。基准用实际样本、错误数和分位值说明能力；性能阈值依据实测基线约定。

`simulation`、`fixture`、`local`、`live`、`device`、`outdoor` 证据分别标注。源码 PR 合入、模型执行结束、用户授权操作、用户验收结果是不同事件。模拟器构建不能证明 iPhone 可安装；安装包和公网 health 也不能证明户外控制闭环。

### 示例：语音会话中切换任务

```text
Given：浏览器已建立已认证的语音会话，任务 A、B 存在，A 版本为 v。
When：在 A 开始 capture，切换到 B，确认该次语音草稿。
Then：草稿及提交仍绑定录音时的 A/v；B 不收到这条指令。
负向：A 的版本或授权失效时，明确拒绝/要求重新确认，不静默转投 B。
不确定响应：保留原 requestId 与原请求内容，先对账或按协议重放。
检查：owner/context/竞态回归 + 服务端重放/版本检查 + HTTP/MCP 跨入口场景。
证据：本地/fixture 可证明这些约束；真实 Linx、Codex 和手机浏览器闭环另需 server-live/phone-live。
```

此例是验收编写示例，不代表这些检查已在本次文档任务中执行。

## 3. 契约优先：先对齐边界，再并行实现

[voice-code-workspace-contract.md](voice-code-workspace-contract.md) 是当前共享接口的权威入口；`docs/contract.md` 只保留旧 v1 路由作为历史兼容记录。架构师提出变更，协调者修改共享文件并组织受影响消费者确认；各入口不得发明不兼容字段。变更先形成可引用的契约 revision，再安排并行消费者；依赖未就绪时使用显式标注的 fixture/adapter。

跨端任务在 Issue 或契约 PR 中回答：

- 谁生产、谁消费；允许的调用方、Mac/项目/任务/版本归属是什么？
- 请求/响应、必选/可选字段、空值、状态与错误语义是什么？
- `requestId` 去重、并发、超时后的不确定结果、取消和恢复如何处理？
- 变更对旧客户端/服务端是否兼容，按什么顺序升级；无法兼容时如何明确拒绝？
- 生产端和消费端用哪些检查证明一致，哪些仅是 fixture，谁负责集成？

例如，`409 blocked` 的无副作用业务拒绝与 `409 conflict` 的请求身份冲突不能混用；手机是否可以清除待提交状态，必须依据共享契约，而非 HTTP 状态码猜测。

接口变更由受影响的生产端/消费端共同检查，并完成各组件既有 review；不额外建立常驻审批委员会。维护有代表性的请求、错误和边界 fixture，用生产端/消费端检查及必要的集成验证保护语义。OpenAPI、JSON Schema 和代码生成可以后续按收益引入，当前不强制迁移工具链。

## 配套约束：模型网关限频与恢复

适用于 agent 可控制的模型网关调用、SDK 和任务调度器。平台内部不可控制的重试不能声称已经实现；本规范不等于当前客户端已有自动退避功能，实现需单独立 Issue 并验证。

1. **识别并共享限额。** 遇到可恢复的 `429`，记录脱敏错误类别、尝试次数和下次可尝试时间；同一限额范围的 agent 共享冷却窗口/速率预算。按网关实际限额区分账户、凭据或模型，不在日志中写凭据。只重试发生限频的步骤，其他独立工作继续。
2. **指数退避并抖动。** 优先解析有效的 `Retry-After`（秒数或 HTTP 日期）。无网关明确策略时，建议起始窗口 2 秒，第 k 次连续限频窗口 `d = min(60秒, 2秒 × 2^k)`，k 从 0 开始；在 `[d/2, d]` 随机取等待值。实际等待取随机值与 `Retry-After` 剩余时间的较大值，后者超过 60 秒时仍需遵守。只保留一个重试责任层，避免 SDK 和外层循环叠加重试。
3. **先降频，再缓慢恢复。** 限频后将受影响的请求速率预算减半，降低并发至至少一个请求，原预算更低时不提高；这里调整的是模型请求预算，不改应用任务执行名额。可先以连续 3 次成功作为恢复信号，每个观察窗口最多增加一个请求并发或 10% 速率，始终不超过原预算/网关上限；再次限频立刻降频并重新退避。参数在任务记录中说明并依据实测调整。
4. **保存任务，避免重试风暴。** 不忙轮询、不让所有 agent 同时唤醒；用调度时间安排下一次尝试。单轮自动重试建议最多 5 次，耗尽后持久保存进度、原请求身份和下次检查时间，转入等待恢复队列，后续由可用调度机制恢复。报告限频状态和可继续的工作；没有持久调度能力时留下可恢复交接并明确说明，不能承诺后台自动续跑。限频本身不表示整个任务被取消或最终失败。
5. **区分不可恢复错误与副作用。** `insufficient_quota`/账户余额或付费限制即使返回 429，也需补充资源，不能无限退避；401/403 需检查授权。独立工作继续，受影响项保留明确阻塞。请求结果不确定时先对账；重试工具/业务写入必须沿用原请求身份和原内容，不能把重新调用模型产生的新工具动作直接重放，造成重复执行。

若后续实现退避器，验收至少覆盖：`Retry-After` 两种形式、退避增长/上限/抖动、共享限额、渐进恢复、重试预算耗尽后的恢复、不可恢复错误分流，以及不重复执行副作用；用可控时钟/随机源验证，禁止向真实网关制造限频压测来证明。

## 架构师检查点与任务模板

沿用 Issue/PR 作为协作记录。架构师分配前检查目标和契约是否齐备；交接时对照验收证据；集成时检查依赖与实际基线；合入后按既有清理协议处理。状态与完成含义按 [AGENTS.md](../../AGENTS.md) 和 [CONTRIBUTING.md](../../CONTRIBUTING.md) 执行。

```text
Issue / Owner / 独占路径：
Base / 依赖 PR / 契约 revision / 生产端与消费端：
用户场景（Given / When / Then）：
正向 / 负向 / 恢复场景与检查命令：
要求的证据类别 / 外部资源与缺口：
模型网关限额范围 / 重试责任层 / 退避恢复负责人（涉及调用时）：
最小可审查切片 / reviewer / 下一检查点：
交接时补：实际 revision、命令结果、未通过项、待验收 gate。
```
