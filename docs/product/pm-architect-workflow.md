# PM、架构师与开发协作

Issue：#32。日期：2026-10-24。补充[Issue 协作规则](../issue-collaboration.md)及[架构师职责](../architecture/README.md)，不改变协调者的路径分配、共享契约、Git/PR 和集成所有权。

## 决策归属

| 角色 | 决定与交付 | 边界 |
| --- | --- | --- |
| PM | 用户问题、三类场景、范围内优先级、产品场景/验收文案；里程碑产品走查和偏差记录 | 不指定安全豁免、修改共享接口、替开发宣布测试通过或代替用户最终验收 |
| 架构师 | 可行性、技术拆分、接口/安全边界、依赖顺序、跨端检查；统筹根 README、模块 README 和构建/安装/部署脚本维护，确保跨模块入口与命令一致、可执行且可安全回退 | 具体改动先由协调者分配路径；不静默缩减产品必交条件，其检查不代替两位独立组件评审；维护部署脚本不授予部署权限 |
| 开发者 | 分配路径内实现、模块使用/配置/测试文档更新、适当回归检查、真实命令与证据、缺口及交接 | 不自行扩展范围/接口/路径，不进行 Git 变更，不自审代替独立评审 |
| 协调者 | Issue/主责与路径分配、共享契约应用、集成、提交/PR/发布记录、资源与用户沟通 | 串行处理共享变更；保留每个门槛的真实状态，不用合入代替设备/户外验收 |
| 用户 | 重大范围取舍、资源与外部动作授权、最终产品验收 | PM 产品走查与 AI 评审均不构成用户接受 |

PM 与架构师共同把“要解决的问题”和“可安全实现的行为”对齐；协调者完成 Issue 分配后，架构师向现有开发者下发技术任务。资源缺失记为阻断，不将原生安装、真实语音或公网控制改写为可选项。

## 一轮最小协作

1. **PM 定义用户出口。** 使用[定位与场景](positioning-and-scenarios.md)，给出一个可独立走查的行为、优先级、失败路径和可观察条件；标明哪些是需求、哪些是假设。避免“体验流畅”“功能完整”等不可判断的条件。
2. **架构师反馈技术约束。** 确认状态/版本/目标/认证/重试语义、依赖和验证环境；风险用可观察影响表述。需改共享契约时，先向协调者提案，契约确认后消费者再实现。
3. **联合冻结任务简报。** 使用下方模板。协调者核对 Issue、基线、排他路径和依赖；架构师安排开发顺序。能在既定范围内解决的实现细节无需重新打断用户确认。
4. **开发交接可复核快照。** 给出实际文件、行为、命令/结果、环境类别及未运行项。架构师检查跨端兼容与安全，协调者集成并按仓库规则发布可验证里程碑；所需独立组件评审单列。
5. **PM 走查产品出口。** 对照已冻结条件检查当前快照，记录通过/失败/未验证、用户可见偏差与下一步；假设未获证据时保留假设。PM 可用 fixture 验证文案/导航，但只标 fixture，不能据此关闭真实服务/真机/户外门槛。

一次走查发现跨端问题时，PM 描述触发、用户影响和期望，架构师定位责任/依赖，协调者重新分配原 Issue 或新独立 Issue。不得由 PM 越过路径边界直接修组件。

每个里程碑的完成定义还包括文档和命令可复现：PM 核对场景/验收文字；开发者更新本模块使用、配置、启动和测试说明；架构师核对根 README 到各模块的入口、参数与构建/安装/部署脚本一致，记录实际可运行命令及安全回退方式。协调者检查这些材料与交付快照相符。缺环境、签名或授权时明确写未验证，不能把脚本存在当作部署成功，也不因维护脚本而扩大外部动作授权。

## 联合交接模板

```text
Issue / 主责 / PM / 架构师：
基线或待评审快照 / 依赖 Issue、PR：
用户与触发：户外用户在 <页面/连接条件> 要完成 <一个决定或动作>。
问题与优先级：<现有障碍、用户影响、P0/P1/P2>。
本轮包含 / 排除：<保持两天范围，列清边界>。
验收条件：给定 <状态/目标/版本>，当 <用户动作>，应看到 <实际结果>。
失败路径：<离线/旧版本/拒绝/限流等具体触发、保留内容、下一步>。
所需证据类别：<simulation/fixture/local/live/device/outdoor，逐项说明>。
假设与未验证项：<假设、如何验证、阻断资源及负责人>。
技术约束：<契约字段、认证/版本/请求身份、安全边界；无变更则写明>。
实现主责 / 排他路径 / 集成负责人：<由协调者确认>。
检查与评审：<实际所需检查、两名独立组件 reviewer、PM 走查出口>。
文档与脚本：<模块说明、根入口/跨模块一致性、实际构建/安装/部署检查及回退；缺项明确记录>。
交接结果：<文件、行为、命令及结果、环境、证据位置、缺口、下一步>。
PM 结论 / 架构师结论 / 用户验收：<分别记录，通过/失败/未验证>。
```

验收条件示例：“给定在 A v3 开始录音、随后切到 B，确认草稿时仍清楚显示 A v3；B 没有收到修改；若 A 已变为 v4，保留草稿文字并要求重新审阅。”工程证明身份隔离；PM 走查用户能否看懂目标及下一步。两者结论分开记录。

## 里程碑门槛

| 里程碑 | PM 单独验证 | 工程/交付证据与限制 |
| --- | --- | --- |
| M1：一个任务可看懂 | 从语音草稿、确认到结果，用户能指出目标、变化、检查与待验收条件 | 本地/fixture 可评审布局和流转；真实 Linx、真实 Codex 与会话续接另需 live 证据 |
| M2：多任务与异常可处理 | 至少 20 任务导航、运行/排队/待处理、录音中切换、离线/授权/停止文案不误导；用户可找到正确任务和下一步 | 调度/去重/版本/隔离回归及 benchmark；四个真实并行任务、十次混合目标指令由实测记录。测试通过不替代手机操作 |
| M3：真实手机闭环可交付 | 同一构建依次走查 A/B/C，真实 diff/检查支持当前版本验收；失败和未验证项清晰 | 同一签名构建的指定 iPhone 安装、麦克风/播报、真实 Linx/Codex、蜂窝→公网 Relay→公司 Mac。写明构建、设备/iOS、端点、连接器与请求身份的受控证据；缺项则门槛未通过 |

每个里程碑记录四栏：**工程检查、独立评审、PM 产品走查、用户验收**。PR、标签、模拟器构建和 PM 走查均不自动让其他栏通过。两天内先暴露硬阻断，再验证单任务和多任务；可验证的文档/源码里程碑可以先发布，最终设备/户外门槛保持开放。

## 分歧与阻断处理

- **需求解释或优先级分歧：**PM 给出具体场景、条件和影响；架构师给出成本/依赖/风险。优先选择能满足现有必交条件的最小实现，记录取舍；改变用户已确认范围时由协调者带明确选项请求用户决定。
- **安全或契约分歧：**架构师说明触发与后果，PM 调整交互使边界可理解；协调者串行确认共享契约。未解决前只暂停受影响任务，其他独立工作继续；不能以演示便利绕过认证或目标固定。
- **是否完成有分歧：**回到冻结的可观察条件和证据。没有所需环境证据就写未验证，失败就写失败；源码完成、测试通过、PM 走查、用户验收分别判断。
- **限流或资源不可用：**保留已写文档/实现及精简 checkpoint，降低重试频率并退避；交接已完成项、未完成项和恢复入口。协调者继续独立工作，不重复创建角色或重新实现已保存成果。

只有必须改变已确认范围、需要缺失资源或外部授权、或现有证据无法消除的关键取舍才向用户提问。问题附具体备选方案、各自验收影响和 PM/架构师建议；可逆的范围内决定由责任角色继续完成。
