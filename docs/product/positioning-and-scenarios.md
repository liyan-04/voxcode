# VoxCode 定位与核心场景

Issue：#32。日期：2026-10-24。以[手机演示版范围](../phone-demo-scope.zh-CN.md)为准；本文件补充问题、优先级和产品验收，不扩大接口或交付范围。

## 定位

**人在户外，用原生 iPhone App 与灵矽 AI 说清小型开发任务，让服务器上的 Codex 执行，再在手机上看真实改动、检查结果并验收当前版本。**

2026-10-24：架构师与PM已完成新方向评估及本地串联简单验证，用户要求按[服务器架构](../architecture/server-execution.md)改造。手机只连服务器；语音和Codex凭据只在服务端。首版一台服务器、一个授权Git项目；公司Mac执行后续可选，AirPlay无协议约束。下文早期公司Mac表述保留历史场景背景，当前按服务器执行解释；已有Mac文件/私有依赖需先迁移，Linux不承担Xcode/macOS构建。实机Linux、真实语音和签名手机仍待验证，不能由本地fixture推导。

首版服务已有授权 Git 项目、暂时离开电脑的开发者。用户的主要困难是：口头需求容易遗漏条件，离开电脑后难以判断执行是否受阻，也难以凭一句“完成了”决定是否接受。VoxCode 把需求、任务、版本和证据连起来，让用户能做下一步决定。

两天内保留一台服务器、一个预先授权Git项目、一个TLS Relay入口和一个同机任务/语音运行入口。原生iPhone安装、服务器上真实Codex、真实灵矽语音与蜂窝VPN远程控制是最终目标。模拟器、fixture 和受控执行器用于开发验证；它们不能替代这个组合交付。交互网页预览、完整 Mac 工作台、后台推送、自定义 AirPlay、任意仓库接管和自动合并任务继续延后。

产品表达聚焦“把口头目标变成可检查条件，把当前版本的真实证据交回用户”。这是待演示的价值假设，不宣称竞品缺少同类能力；比较须沿用[有来源的竞品调研](../research/competitors-mobile.md)。

## 三个核心场景

### A．离开工位后修一个可复现的小问题

用户在户外停下后打开 App，选择已配对的服务器项目，说：“修复名称只填空格也能保存的问题，保留正常名称的保存行为。”灵矽形成可编辑草稿；必要时只澄清影响范围。用户确认目标和验收条件后才执行。

手机显示真实执行状态与最近活动。完成后先给变化摘要、变更文件和检查结论，再允许展开包含新增文件的 diff、检查命令、退出码及关键输出。用户对照“空白被拒绝、正常值仍可保存”逐条人工确认；不满足时提出同任务追问，新版本重新验收。

**可观察验收：**一条真实灵矽录音形成草稿，确认前没有代码执行；确认后真实 Codex 修改授权项目。手机能查到该版本的实际 diff 与检查证据；追问沿用同一 VoxCode 持有的会话，旧版本的通过记录不能通过新版本验收。必选条件失败或未验证时不能接受。

### B．在外等候时切换多件独立工作

用户同时安排输入校验、空列表处理、帮助文案和一项测试补充。四件工作各自执行，第五件排队；任务列表还保留以前的任务。用户先看“运行 4/4、排队 1、待处理 N”，点短编号切换，或说出任务名；重名时先澄清候选。

在 A 开始录音后，即使切到 B，录音草稿仍标明 A 和录音开始时的版本。用户确认前能看见目标；混合“切到 B，再修改”的指令先确认 B，再形成 B 的草稿。独立任务互不覆盖，有代码依赖的任务顺序执行，首版不自动合并。

**可观察验收：**指定 iPhone 能浏览/筛选/切换至少 20 个持久化任务；四个真实独立任务执行，第五个排队。至少十次混合目标指令包含录音中切换，错误任务修改为零；版本过期、重名和歧义都要求重新审阅。调度配置 1–8 及名额不超限另以工程检查证明，不据此承诺八路真实执行速度。

### C．蜂窝信号恢复后处理阻塞并检查结果

用户发出任务后经过弱信号区域，回到 App 时看到最后同步时间和“连接中断，显示上次状态”。恢复后取回实际快照；若提交响应曾丢失，先对账原请求，不能点一次重试就执行两次。

任务需要操作授权时，手机显示实际操作、范围和所属任务，由用户允许或拒绝；授权不等于结果验收。检查失败时提供命令、退出码与输出，允许同任务追问。用户停止任务后看到“停止中”，确认终止才显示最终状态；取消不承诺撤销文件改动。执行进程无法安全恢复时明确提示需要服务器运维核对。

**可观察验收：**蜂窝手机断网一分钟再恢复，能取回真实状态；同一请求重试无重复创建/执行。授权单次生效、旧版本授权被拒绝；停止确认前不释放名额。失败、未验证和待验收在手机上可区分，不能把无新事件显示为持续正常执行。

## 手机优先回答的四个问题

| 用户问题 | 首层信息与下一步 |
| --- | --- |
| 我在控制哪里，状态是否新鲜？ | 服务器/项目、连接状态、最后同步时间；离线保留快照并标旧，不显示为当前正常状态 |
| 哪件事需要我处理？ | 任务短编号、标题、真实状态、最近活动；待处理入口带回授权、待输入、失败或中断的所属任务 |
| 工作到了哪里？ | 排队/运行/等待输入/等待授权/停止中/中断/失败/执行完成；运行与排队数量。显示事实和等待原因，不显示估算百分比 |
| 我能接受吗？ | 当前版本、改动摘要、文件/diff、检查命令/退出码/输出、逐条条件和未验证项；检查通过、操作授权、用户验收分别呈现 |

Issue #25 的手机监控提案（独立工作区 `docs/architecture/phone-monitor.md`，尚未作为本基线契约）若集成，应服务上述问题：主入口显示控制连接、同步新鲜度和待处理任务；Settings 内的状态页承载 Relay 请求计数、耗时、服务器Node内存和组件配置等诊断。`codexAvailable`/`voiceConfigured` 只能说明可执行文件/配置存在，不能显示成真实模型或语音已可用。监控读取失败不清除已成功取得的任务结果；显示旧快照、未知状态和重新刷新动作。提案合入前仍按现有[契约](../contract.md)执行，产品文档不自行开放远程监控路由。

## 两天优先级与产品出口

| 优先级 | 顺序与出口 |
| --- | --- |
| P0：先打通核心链路 | 尽早探测签名安装、真实 Codex 修改/续接、真实灵矽录音/播报；先完成场景 A。硬阻断出现时停止增加次要功能，保留真实失败记录 |
| P1：完成已承诺的控制可靠性 | 完成 B/C 的多任务、目标固定、重试、恢复、授权、停止与版本验收；在已授权范围内解决 SSH 认证并验证 Relay 公网链路。它们仍是必交要求，排在单任务之后不代表可省略 |
| P2：有余量再改善诊断 | 可理解的状态页和折叠诊断；不新增监控平台、部署单元或后台能力 |

每个可验证里程碑由 PM 单独核对：用户是否看懂目标/状态、能否找到阻塞任务、是否能基于当前证据决定下一步。工程检查和两位独立组件评审由各责任人提供，PM 不代签技术通过。最终演示须让同一签名构建在指定 iPhone 上通过vm6 TLS Relay控制同机真实Codex，并完成实际灵矽语音；PM 检查用户路径，用户作最终验收。记录构建/版本、环境和证据类别，尚未执行的项保持未验证。
