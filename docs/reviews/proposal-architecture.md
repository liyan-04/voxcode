# 产品方案架构评审

日期：2026-10-23。评审对象：`docs/product-proposal.zh-CN.md` 讨论稿。角色：系统架构与灵矽集成独立评审。本文仅给出方案建议和阻断歧义，不修改原方案、源码、测试或既有评审，不执行构建、协议探针、联调或部署，也不代表用户已确认范围。

## 结论

“原生手机控制 + Mac 本地 Codex + Mac 主动出站中继 + 灵矽设备语音/MCP + 固定 Web 项目预览”的方向成立。自有 Codex 会话、显式提交、任务版本、前台同步、异常重启后本地恢复等边界均有必要。

当前文稿适合确认产品方向，还不足以作为无条件的两天交付承诺。未发现需要放弃总体方向的 P0；以下 P1 是进入实现前应确定的架构或验收边界，不是对当前源码新增漏洞的判断。建议先确认资源与三份契约：连续会话、语音草稿、预览授权，再恢复并行实现。

评审期间已复核主方案修订：固定 Web 项目构建后的静态 SPA，前端测试数据，不承诺后端、HMR、外链、WebSocket 或 Service Worker；独立 preview origin、task/version 限权 HttpOnly cookie、原生认证引导和隔离的 WKWebView 数据存储，不让页面获得控制 bearer；明确条件/证据版本、资源门槛和方案批准不恢复部署。以下预览评估按该修订更新，不把它当成用户已批准的范围。总体上，该收敛没有发现架构上不成立之处。

## 最关键三项

1. **P1：连续 Codex 会话需要持久身份和提交对账契约。** `taskId`、代码版本、Codex `threadId/turnId`、提交 `requestId` 不能混为一个“会话”。特别是“版本变化后重新确认”不得改写已提交但响应丢失的请求；恢复历史不等于确认旧执行已结束。
2. **P1：灵矽的设备 WSS/MCP 路线成立，但还需闭合草稿回传与实际播报。** 工具需要把有版本的草稿可靠交给手机确认；MCP ID 不能代替最终提交 ID。需要确定使用设备侧 MCP，明确前台询问后播报，并把真实 MCP 调用及 Opus 原生播放纳入早期能力关口。
3. **P1：AirPlay 原题口径仍需外部确认，真实能力仍是交付门槛。** 资源 T0、首轮可听播报/会话续接/受保护预览和部署须单独恢复，已写入主方案，原有工期歧义已处理。尚不能由架构评审替代的是主办方认可“Mac 系统 AirPlay”路线，以及账号、真机和公网实际可用。

## 逐项意见

### A. 公网链路与资源关口（方案已明确，待实际满足）

依据：方案第 6、9、11 节。

Mac 主动出站 WSS 是符合公司网络场景的选择，中继作为可信转发方处理手机 bearer/任务/音频，方案明确不宣称端到端加密，这个表达准确。但指定 `IP:9899/TCP` 尚不是 iPhone 可用的入口。需要确认实际外部 URL、域名/证书管理者、TLS 终止位置、9899 对应的监听职责，以及公司代理/防火墙是否允许该 WSS 长连接。部署继续保持暂缓；以后恢复时必须重新检查 9899，已占用则停止并通知，不能复用已有服务。

修订稿已经把资源准备与首轮探针前移，并明确方案确认不恢复部署。公网检查只能在用户另行明确恢复部署后安排；不能把“完成方案确认”当作执行该检查/部署的许可。连接状态建议至少区分“手机至中继失败”“中继可达但 Mac 不可达”“Mac 可达但 Codex/Linx 不可用”；Mac 断线/休眠时，手机保留最后状态与时间，不推断实际进程已经停止。

语音和预览会扩展中继的职责，应提前决定有界传输方式。输入 PCM、输出 Opus、截图与预览资源不能挤占取消/授权/状态请求的全部队列。需要约定独立额度、顺序/丢失处理、超时、断线后哪些消息可重放，以及 revoke 如何终止仍在传输的会话。两天内固定一个语音上传节奏和一种下行方式即可，不必承诺任意流协议。

主方案第 11 节已列出资源责任建议；恢复开发前落实具体负责人和可用时间即可。这里保留为实际交付门槛，不再列为方案遗漏。

### B. 真实 Codex 连续会话（P1）

依据：方案第 2、3、6 节和“连续上下文”“断线与重试”验收项。

官方 OpenAI Docs 将 thread 定义为包含多个 turn 的会话，并提供 `thread/start`、`thread/resume`、`turn/start`；因此“追问继续 VoxCode 持有的 thread”是有公开接口依据的路线。公开文档不是已安装版本兼容、账号可调用或本地持久化成功的证据。恢复同一 thread 也不证明旧执行进程已经退出，更不能自动消除响应丢失后的重复 turn 风险。

建议明确以下契约：

- 每个任务保存授权项目、固定 worktree、Codex thread ID、任务版本、当前/最近 turn ID、提交 request ID 与不可变指令。追问沿用 thread；重新创建 thread 必须显示上下文变化并由用户确认。
- 第一版对同一任务只接收一个活跃 turn。运行中的新指令先进入待确认/待执行状态，或明确拒绝；不在首版同时承诺 `turn/steer` 的中途修改语义。
- “录音后任务已更新”仅适用于尚未提交的草稿。可以刷新当前版本后重新审阅，形成新的提交；已经提交但结果未知的请求必须保留原路径、原版本、原内容、原 request ID，先查询/恢复其结果，不能自动换版本再投递。
- Mac/App Server 重启后，先确认执行所有权与旧 turn 结果，再恢复 thread。响应未知时显示待恢复，不默认重新执行。摘要重建不是原会话恢复，应有单独标识。
- 恢复 thread 时重新验证工作目录和权限策略，不能因为保留历史而继承扩大后的权限。现有 Desktop 聊天继续保持不在首版承诺内。

建议用户确认后的最小验证出口包含：真实创建文件、一次追问引用上一轮决定、重启后恢复同一任务、丢失提交响应不重复执行。只验证 initialize/thread 创建不足以证明连续开发。

### C. 灵矽 MCP、上下文和草稿协议（P1）

依据：方案第 5 节。

设备侧 MCP 与 Mac 建立的设备 WSS 配合，能够避免为首版新增公网云端 MCP 入口。已读灵矽文档中，平台充当 MCP client，设备侧实现 server，依次通告能力、initialize、tools/list、tools/call。第三方应用文档另描述平台向业务服务发起 SSE 请求的集成路线；两者不应在实现时被无意混用。

建议确认首版固定“设备 WSS + 端侧 MCP”路线，第三方 SSE 仅作为参考或另案。工具白名单中的只读/草稿边界正确，但还需补齐：

- 由服务端为每条语音会话建立 `phoneSession -> authorizedProject -> frozenTask/version` 映射。工具参数不能自行指定手机身份、项目目录或扩大目标。语音连接仍在但手机凭据撤销/过期时，工具应立即失效。
- `propose_task/propose_followup` 写入的是服务端草稿，返回有 TTL 的 draft ID；草稿记录原语音会话、目标版本、验收条件及生成来源。手机能可靠取得、编辑、确认它，不能只把 JSON 留在模型回复里。
- MCP RPC ID 只负责该语音连接内的调用去重。最终手机提交另有持久 request ID，并引用被确认的草稿；STT 直接提交和 MCP 草稿提交必须汇合为同一个待确认对象，不能形成两条执行入口。
- 工具真正执行 JSON Schema/字段长度/任务访问校验，设置超时和响应体限额。查询的任务状态与证据带版本和时间；模型生成的解释不能取代真实工具结果。
- 任务切换只是导航提议。当前录音仍绑定原任务；后续新语音会话重新绑定目标。不得在现有连接上悄悄改变 frozenTask。

已读 WebSocket 文档提供 `hello.agent_params.custom_replace_prompt` 来替换智能体预先配置的提示词占位符。可用它传入已授权的精简标签/约束；任务进度仍应由工具即时读取。需要准备匹配的智能体提示词模板，不能假定附加任意 JSON 后模型自然获得正确上下文。

没有发现“Mac 软件端无法实现设备侧 MCP”的文档障碍，但设备注册/绑定状态仍须真实确认。能力探针除识别语音外，应包含平台主动 initialize/tools/list 和一次 get_task_status 调用、一次 propose_task 后手机取得草稿；核对实际握手顺序，不从单独的 WebSocket hello 成功推断 MCP 已协商。若短轮次会重建 WSS，澄清产生的草稿/验收条件仍应保留在服务端，不依赖云端自动跨连接恢复全部记忆。

### D. 原生 TTS 与短轮次语音（P1，关键路径）

依据：方案第 5、9 节和“灵矽语音”验收项。

方案正确指出“收到音频帧不等于手机播报”。灵矽官方文档明确服务器 TTS 为 Opus，通常单声道 16/24 kHz，帧长 20/40/60 ms，并区分正常结束和打断后的 stop。PCM 输入 hello 不能推导为 PCM 输出；原生 App 也不能把裸 Opus 帧当 WAV/Ogg 文件直接播放。

需要在方案确认后尽早选择并验证一个实际原生解码路径及其构建/许可依赖。定义保留服务端输出元数据、有界顺序缓冲、播放结束、打断清空，以及切换麦克风/播放音频会话的状态机。首版半双工足够：说话时不播报，播放中用户再次按下录音先中止旧播报并清空旧音频；只中断语音，不取消 Codex。关闭面板/后台/凭据撤销后旧音频不能在下一次面板里继续播放。

还需确认“结果播报”是用户前台打开面板并询问后播报，还是任务完成自动推送播报。建议两天首版选择前者，与不承诺后台通知一致。后者涉及长期语音会话、结果触发和后台行为，应另设验收，不能从已接通 MCP 查询自动推定。

### E. 收敛后的静态 SPA 预览（P2 实现约束）

依据：方案第 7 节和“手机验收”“证据与版本”验收项。

固定构建后静态 SPA、独立 preview origin、任务/版本限权 cookie、原生认证引导和隔离数据存储，已经覆盖原稿“同源可执行页面是否获得控制身份”的主要歧义。该选择仍是真实可操作预览：表单校验、页面切换、前端状态和测试数据交互都可验收；但不能将模拟 API 演示称为真实后端/短信/业务集成。此处不重复移动端 cookie/WebView 细节。

架构上剩余应明确的是产物发布边界：

- 主方案已经要求后续版本不覆盖旧快照。实现契约进一步把快照登记为不可变 artifact ID，并绑定任务、输入版本、构建结果和摘要；静态服务读取产物快照，不持续读取 Codex 正在编辑的工作区。
- 产物发布只允许约定目录中的普通文件，拒绝越界路径/符号链接、目录浏览和源码/私有配置泄漏；入口页面的 SPA 路由回退不能回退到任意本机文件。构建本身使用固定配方并剥离桥接凭据。
- “模拟 API”优先是打包在 SPA 内的前端测试数据；如确需服务端 mock，也仅有固定、无副作用的只读路由，不能顺手扩大为任意后端转发代理。资源打包在产物内，禁止外链与外部请求应有对应限制。
- 独立 preview origin 的 DNS/TLS 与中继路由要进入 T0 资源表。静态文件/截图仍需大小、并发、保留和撤销额度，不能与控制请求共用无边界队列。无需每个任务长期运行一个开发服务器，可以用统一受控静态服务按 artifact 路由，减少两个任务的端口/进程复杂度。

主方案“独立预览端口/端口分配”的表述可在技术契约中澄清为资源隔离要求，不必强制每个任务一个 dev server。版本化静态产物不等于版本化 worktree：后续任务仍可继续编辑，已发布预览保持可追溯。

### F. 双任务隔离和版本证据（P2）

依据：方案第 3、6 节和“并行与切换”“证据与版本”验收项。

方案已正确承认 worktree 不是完整安全沙箱。建议把任务资源落为一张清单：task ID、cwd、thread ID、运行版本、artifact ID、临时目录、数据目录和所属进程。以任务为单位清理；不能用进程名全局终止其他 Codex。按静态 SPA 收敛后无需强制为每个任务保留开发服务器端口。

两天演示优先无共享数据库、无生产凭据的 Web 项目。测试目录、缓存和后台子进程仍可能共享；不能把“最多两个模型 turn”描述为系统资源完全隔离。并发构建、静态产物和截图也需独立额度。任务间依赖继续顺序执行，不做自动合并。

验收通过应引用当时的代码/产物版本与证据。后续修改使旧验收失效，预览、截图和检查结果一起更新；在文件仍变化时，不把旧测试成功当作新版本成功。

### G. AirPlay 原题适配和两天范围（P1/P2）

依据：方案第 8、9、14 节和“现场屏幕”验收项。

方案坦诚列出“Mac 系统 AirPlay 镜像是否算完成原题”的未决条件，这是必要的。公网远控能力不回答题目的屏幕连接要求。**主办方口径是 P1 范围门槛**：需要确认 AirPlay 的发送端、接收端、现场网络和“应用是否必须直接发现/选择屏幕”。若原题要求应用内 AirPlay 控制，不能在最后录屏时才发现系统镜像不被认可。

**16-20 小时仍是带条件的估算。** 修订已把原生安装、真实修改、可听播报、会话续接与受保护预览放到首轮探针，公网明确等待部署恢复授权，这处理了原来的排期歧义。持久 Codex 会话、MCP 草稿和下行音频仍有跨端关键路径；多 Agent 不能消除共享协议依赖。建议各端两位独立评审随接口与功能完成滚动进行，最后半天用于修复/复测。

建议确认后的交付节奏为“资源关口 -> 单任务真实闭环 -> 同一任务追问与结果预览 -> MCP 查询/可听播报 -> 双任务与故障演练”。这些都是方案必交项时，前一关失败就暂停新增功能并明确剩余缺口。可以缩减演示项目、界面精修、HMR和自动播报，不应削去已确认的原生、户外、真实灵矽、连续上下文及交互预览却仍宣称完整验收。

## 建议在恢复实现前确认的决策表

| 决策 | 建议默认值 | 未确定的后果 |
| --- | --- | --- |
| 连续会话 | 自有持久 thread；同任务一个活跃 turn；失败恢复先对账 | 追问上下文或重试可能重复/丢失 |
| 灵矽集成 | 设备 WSS + 端侧 MCP；只读和草稿工具；显式手机提交 | 可能混入公网 SSE/MCP 和第二执行入口 |
| 结果播报 | 用户前台询问后播报；半双工可打断；明确 Opus 原生解码路径 | 两天范围扩展到长期会话/后台提醒 |
| 预览 | 固定静态 SPA 和测试数据；独立 preview origin；任务/版本受限 cookie；不可变产物；无后端/HMR/外链/WS | 实现者仍可能启动 dev server，或旧页面被新工作区内容覆盖 |
| 资源与计时 | 明确提供者；资源关口通过后计算有效实现时间 | 外部等待与工程工时混在一起 |
| AirPlay | 先获主办方对“Mac 工作台 + 系统 AirPlay”的认可 | 最后阶段可能需要改变产品路线 |

## 资料与验证边界

本评审只阅读方案、已有设计/需求记录，并只读获取以下官方公开文档；没有运行 Codex、灵矽、iOS、预览或公网联调，没有验证账号权益或已安装版本行为。

- [OpenAI Docs：Codex App Server](https://developers.openai.com/codex/app-server/)：thread/turn 生命周期、thread/resume、安装版本专属 schema；公开文档支持可选路线，不代替本项目协议验证。
- [灵矽设备 WebSocket](https://linx.qiniu.com/docs/xrobot/platform/websocket)：设备绑定/鉴权、hello 提示词参数、listen/abort、TTS 状态与 Opus 输出。
- [灵矽端侧 MCP](https://linx.qiniu.com/docs/xrobot/mcp/hardware-mcp)：平台 client/设备 server、工具发现与调用。
- [灵矽第三方应用](https://linx.qiniu.com/docs/xrobot/guide/third-app)：与端侧 MCP 不同的业务 SSE 路线，列出差异以避免隐式扩展范围。

公开文档只能证明接口描述存在。真机安装、音频解码、会话恢复、真实模型修改、可信公网和 AirPlay 现场验收仍全部以用户确认后取得的实际记录为准。
