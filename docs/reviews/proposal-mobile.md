# 移动端与两天交付方案评审

日期：2026-10-23。范围：仅评审 `docs/product-proposal.zh-CN.md`，对照需求核对、原设计和共享契约；不评审或修改实现，不运行测试、联调或部署。既有录音启动竞态保持待修。本报告不是原生构建或真机认证。

## 总体判断

方案方向覆盖了原始移动需求：指定 iPhone 上的原生 App、蜂窝网络控制公司 Mac、灵矽语音协作、双任务切换、真实结果检查和用户验收。前台同步、一个授权项目、一种固定 Web 演示项目的收敛合理。不能把“完整方案可行”解读为“现有代码已经交付”或“两天内必然完成”。

建议有条件确认产品方向；确认两天交付范围前，先明确下面三个决策缺口。已有 Desktop 聊天是否必须接管，以及系统 AirPlay 是否满足题意，仍需由用户/主办方确认，不能由技术评审替代。

## 三个优先决策

### 1. 交付资源需要成为开工前提，公网与播报验证应提前

对应方案第 9、11、13 节，尤其第 171、173、206–210、226 行。

原生安装、真实 Codex 写文件、灵矽识别、手机播报、受控预览、会话连续性和公网链路仍有实质缺口。当前计划把可信公网接入、播报和预览放在第二天，容易直到最后才发现 iOS ATS/证书、公司出站策略、音频编码或 WebView 资源请求不可用；多 Agent 不能消除这些外部依赖。前两小时可以作为探针验收窗口，不能同时默认覆盖完整 Xcode 的准备、账号申请和签名排障。

建议方案补一张资源责任表：可用于构建的 Mac/Xcode 与磁盘空间、指定 iPhone/iOS 版本、签名团队和安装途径、TLS 域名/网关负责人、公司 Mac 出站/供电条件、灵矽设备/语音权限与输出格式、固定演示仓库及启动命令，并给出最晚就绪时间。比赛交付默认选择指定设备的开发安装；TestFlight 另列为可选分发方式，不能成为未验证的安装捷径。

恢复实施后的第一条纵向探针应尽早证明“签名安装 → 实际 HTTPS 配对 → 一段真实识别 → 一段可听播报 → 一次真实修改 → 手机打开一个已认证页面”。资源未齐时如实保留阻断，不把听写、截图或本机网络改称最终交付。当前部署仍暂停；批准产品方案不应被自动解释为恢复远程部署授权。

### 2. 手机验收需要明确的版本化记录，预览需先限定可支持的浏览行为

对应方案第 3、4、7、10 节，尤其第 37–42、68–74、149–155、188、194 行。

“验收条件与证据对应”是方案的产品重点，但尚未说明条件由谁确认、如何保存、追问时如何继承、哪些必须人工验证。当前共享契约只有任务版本和一般 evidence 列表，没有独立验收条件或验收快照；若不先补设计，很容易落成模型摘要加一个“验收通过”按钮，手机仍不能可靠判断某条需求是否实现。

建议方案确定最小记录：用户确认的条件清单、所属任务版本、对应的检查/截图/预览证据、通过/失败/未验证状态、人工检查结果和验收时的版本。不要把一条测试通过推导为所有条件通过。明确必选条件未验证/失败时是禁止“通过”，还是允许用户注明原因接受；不由模型默认为通过。追问增加版本，保留旧条件和证据的历史关联；离线或版本已变化时不能凭旧页面完成当前版本验收。验收仍只表示用户接受结果，不自动合并、推送或部署。

预览的计划还应选定一种最小技术路线及支持矩阵，例如固定 Web 项目的构建后页面、相对资源和同源导航；是否支持后端接口、表单、刷新和外链必须写清。仅给 WKWebView 首次导航添加 bearer 不代表图片、脚本、后续导航也带有授权。预览应使用受任务/版本约束的独立凭据，页面代码不得获得控制任务的通用 bearer；凭据如何用于子资源、撤销和缓存失效，应在接口方案中说明。两个任务更新时必须能证明手机看到的是各自当前版本。截图仍是辅助证据，不能替代已承诺的可操作页面。

### 3. 录音固定目标与语音切换、版本重确认之间仍有歧义

对应方案第 3、5、10 节，尤其第 48–50、92、104–105、191 行。

“录音开始固定任务/版本”与“原任务更新后重新确认当前版本”需要区分两种情况：从未提交的草稿可以由用户审阅后形成新版本的提交；结果不确定的旧提交只能用原 requestId、原版本和原内容重试。不能把更新版本号后复用旧 requestId 当作重新确认。

建议确定以下可直接验收的规则：

- 一段录音及后续澄清共同属于开始时的明确目标；纯导航切换只影响后续新录音，不改变已有草稿。说“切到 B，再把按钮改红”时先确认切换并开启新的 B 草稿，不能把后半句静默落到 A 或 B。
- 从未提交的草稿遇到版本变化时，展示原/当前版本与保留的文字，要求用户重新审阅目标、内容和条件，再产生新的提交身份；不自动重放。结果不确定的提交先对账，保留完全一致的重试。
- 单路语音明确采用点击开始/停止或按住说话中的一种首版交互；“打断播报”明确为停止播放按钮还是自动语音打断。后一种需要额外的音频会话与回声处理验证，不能由“轮流说话”默认推出。
- 锁屏、来电、耳机切换或网络失败时停止捕获，保留可编辑草稿并显示原因；回到前台不自动录音。丢弃/重启后，旧创建请求的成功、失败、音频、转写和播报返回均不能修改新会话。已记录的启动失败竞态在恢复开发后应优先修复。

十次路由验收应包含录音中切页、混合切换指令、澄清中切页、任务版本变化、响应丢失重试及快速丢弃/重录；不能只测十次顺序点击提交。

## 两天范围建议

保留最终必交：指定 iPhone 原生安装、蜂窝网络真实闭环、灵矽澄清/进度查询/结果播报、同一任务追问、两个任务隔离、一种可操作预览、版本化证据与明确验收。既然方案将工具查询和播报定义为语音协作交付条件，不能在演示时将它们悄悄降为可选。

可缩减工作量：一种录音手势、一个固定小型 Web 项目、短轮次对话、最少只读查询/草稿工具、指定设备开发安装、简单的手机条件清单。APNs、自动合并/发布、任意框架、全局会话搜索和 Desktop 接管保持范围外，但 Desktop 边界必须先由用户接受。

建议把预览/会话恢复的专家评审放到设计确定时，真机音频/前后台检查放到首个可安装版本时，第二天下半段只留复核与演练。否则直到最后才处理证书、音频和预览权限，16–20 小时没有足够返工空间。AirPlay 的主办方口径与真实接收端资源也应提前落实。

## 当前结论与限制

产品方向可以进入确认讨论；两天完整交付的承诺应以资源就绪和上述决策明确为条件。当前保持方案阶段，未修改源代码、测试或既有评审文件，未执行联调、构建、部署或提交。本文提出的资源和行为验收均为建议，未将其记为已经验证。
