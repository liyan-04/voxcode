# Independent iOS implementation review

Reviewer: independent iOS/platform and correctness reviewer; did not implement this client. Date: 2026-10-23.

Reviewed revision: **6745dc03d61d2034a5e58f7ec7dea4bf205b97e2** in `.worktrees/ios` (HEAD verified). Scope: native Session/Composer/TaskDetail, recording generations, PCM player, core transport/trust, simulation and tests. This review does not approve later implementation changes.

## Findings

1. **P1 — A definitive rejected submission permanently locks the persisted composer.** `apps/ios/VoxCode/ComposeView.swift:103-110` creates/persists `pending` before sending and only clears it on success. `apps/ios/VoxCode/Session.swift:66-68` reduces all errors to Bool, losing the distinction between an uncertain response and a definitive `400 invalid` / `409 stale`. With pending set, editing and version rereview are disabled (`ComposeView.swift:39-45,53,77`); the only action sends the same rejected payload. Closing preserves the journal, and `VoxCodeApp.swift:29,41,47` blocks new work in favor of recovering that same request. A normal task-version change between confirmation and dispatch therefore requires local forgetting/re-pairing rather than a safe rereview. Preserve immutable retry for uncertain network/5xx outcomes, but expose typed HTTP/business rejection, clear rejected pending state/journal, retain text/conditions and allow explicit rereview with a new request ID. Do not classify every 409 as harmless: an idempotency conflict can require reconciliation. Regression: stale-version rejection preserves draft and enables rereview; invalid input enables correction; timeout/unknown response keeps exact payload/requestId across relaunch. Findings were sent directly to `ios_v1` as IOS-004; no fix was reviewed here.

2. **P2 — Other definitive operation failures also have no recovery action.** `apps/ios/VoxCode/TaskDetail.swift:79-83` retains pending on all failures and disables cancel/approval/compose controls; `TaskDetail.swift:126-131` does the same for criterion decisions. An expired approval or stale criterion can only be retried indefinitely while the detail/sheet remains open. Apply the same typed-rejection handling as finding 1. A fresh snapshot should permit reviewing the current operation, while an uncertain response must retain the original request. Regression: expired approval, stale criterion, and lost successful response each have distinct recoverable behavior. These pending values are not persisted, so this is less severe than the composer lock.

3. **P2 — Re-recording can race the old session's asynchronous deletion.** `apps/ios/VoxCode/ComposeView.swift:90-94` awaits `discard()` then immediately starts a new recording. `apps/ios/VoxCode/Recorder.swift:122-126` clears local identity but launches DELETE in an unawaited Task, so awaiting discard does not establish that the server released the old recording. With the single-device active-session constraint, the next POST can arrive first and receive 429, discarding the new startup. Keep local cleanup immediate, but order the next session creation after bounded remote cleanup, or reconcile/retry the new create using its unchanged request ID. Regression: delay DELETE completion, press re-record and verify either ordered success or an explicit retry without losing text. This is a source-level lifecycle finding, not a reproduced live/network failure.

4. **P2 — Older refresh/replay responses can replace newer task snapshots.** `apps/ios/VoxCode/Session.swift:46-55` guards only the pairing/mode revision, not ordering of requests within that revision. Root polling, pull-to-refresh and foreground refresh can overlap (`VoxCodeApp.swift:43,48-49`); an earlier response can overwrite a newer completed snapshot or a successful mutation applied at `Session.swift:68`. An idempotent replay can likewise return an earlier task version and replace a newer local one. Server version checks prevent accepting the wrong version, but the UI can regress state and trigger the locked stale flow in finding 1. Use ordered refresh ownership and preserve a mutation/newer-version barrier rather than assuming response completion order. Regression: return a newer refresh/mutation first and an older refresh/replay afterward; displayed task version/status must not regress.

No P0 identified. Findings 1-2 are definitive control-flow defects; 3-4 need targeted native/transport regression tests. No source edits or attack simulation were performed.

## Checks that support the design

- Recorder freezes target/version/requestId before permission/network awaits (`Recorder.swift:23-30`); startup, taps, uploads and poll results verify their generation. Old permission/request failures do not discard a newer generation. Discard/interrupt invalidate callbacks, cancel uploads and stop capture/playback; stop drains ordered uploads. No automatic background resumption is implemented.
- VoiceDraft.prompt **is used**: `Recorder.swift:61-63` validates the frozen target/version/expiry and writes proposal.prompt to transcript. `transcriptEdited` prevents later STT/drafts overwriting manual prompt edits (`lines 59,63`). Composer separately protects manually edited title/criteria (`ComposeView.swift:96-99`). No missing prompt integration was found. Add a native test combining these paths; existing core draft validity tests alone do not exercise SwiftUI edit preservation.
- Evidence is separated by task version, manual criteria and final acceptance are distinct, and acceptance requires completed/current-version required conditions. An uncertain mutation keeps its original route, payload and requestId. Offline snapshots remain inspectable and mutation controls depend on connectivity.
- PCM decoding validates signed little-endian frames, supported rate/channels, size and sequence. Playback is bounded to four seconds, generation-protected and suppressed immediately after stop/abort. Input recording discards returned audio to avoid feedback. Actual AVAudioSession behavior and audible playback are not established by core checks.
- The client uses root HTTPS origins, pairs without sending the previous token, stores origin/token atomically in Keychain, rejects redirects, disables cookies/cache and restricts fixed-IP trust to the bundled CA with exact IP SSL policy. Ordinary HTTPS uses system trust. Missing/invalid/expired private CA fails closed; no production CA is committed. No external endpoint or credential was accessed in this review.
- Simulation is explicitly toggled, off at launch, visibly labelled, uses fixture task/evidence text and disables voice. The actual simulation transport preserves request replay and version-separated evidence; it makes no live Codex/Linx claim.
- Maintainability: stateful SwiftUI logic in Composer/Session/TaskDetail needs direct fixture coverage; current core tests validate value types but do not exercise response classification or overlapping Session updates. Small extracted mutation-result/retry policies would make these tests possible without a UI redesign.

### Resolved findings

- **Original P1, persisted definite-rejection lock: resolved in source.** `Core.swift:139-151` preserves HTTP status and classifies only `400 invalid`, `409 stale`, and the independently reviewed Mac `409 blocked` as definite rejections. `Session.swift:72-88` clears a matching journal only on success/definite rejection, matching both route and request ID. `ComposeView.swift:108-123` retains the current instruction/title/conditions, releases local pending, closes prior voice ownership and creates a fresh attempt identity after definite rejection; a changed task version still requires explicit rereview. Timeout, malformed response, generic conflict, unknown status/code, 401, 429 and 5xx remain uncertain and retain the immutable submission. This deliberately preserves an earlier uncertain outcome even if its subsequent retry receives 401.
- **Original P2, detail/criterion rejection lock: resolved in source.** `TaskDetail.swift:84,132-133` clears local pending for definite rejection, keeps uncertain operations retryable with their original payload, refreshes state and shows operation errors. Stale criteria can be closed and reopened against the current version.
- **Original P2, known-session DELETE/create race: addressed in source for a known session.** `Recorder.swift:25-34,126-131` freezes the new generation, awaits a shared cleanup barrier before permission/create, and queues/awaits deletion of the old known ID. Local generation invalidation still happens immediately. `FrozenRecording.nextAttempt` and `ComposeView.swift:90-95` renew the request ID only for an explicitly closed recording attempt, retaining task/version. Explicit discard during startup marks its attempt closed even before a server ID is known; a late successful response deletes only that discarded ID. Unknown create failure retains its original request identity. The new native fixtures cover delayed DELETE, late successful create after a newer start, unknown create failure and preserved target. Unknown/failed remote deletion is still best effort; this is not a promise that network failure proves provider termination.

### Remaining finding

**P2 — Equal-timestamp replay can still regress same-version task state.** `apps/ios/Sources/VoxCodeCore/Core.swift:174-178` accepts an incoming snapshot when its version and `updatedAt` equal the current snapshot (`next >= previous`). `Session.swift:79-81` applies that comparison to mutation/replay results. A cached create response showing queued and a later running/completed snapshot can share the same millisecond timestamp; if the cached replay is issued after the fresh snapshot, it owns the current request generation and is accepted. The Mac uses millisecond ISO timestamps, so equality does not imply identical task contents. The new request-generation ownership correctly prevents older in-flight requests from winning and strictly older versions/dates are rejected, but it does not close this equal-time case. The added native ordering fixtures use different versions/timestamps and do not test it. Keep an already newer observed state on ambiguous mutation replay and refresh authoritatively, or introduce an unambiguous server snapshot ordering marker; do not simply reject all equal-time refreshes, because evidence can update without advancing execution-input version. Add a same-version/same-timestamp/different-status replay regression. Reported to root and `ios_v1`; no resolving source was reviewed here. This is a residual of original finding 4, not a new P1 or an authorization bypass.
